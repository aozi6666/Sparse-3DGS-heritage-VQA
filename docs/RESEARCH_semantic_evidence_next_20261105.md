# 语义时间选择：源码复核、离线诊断与下一步研究设计

2026-11-05。目标为可重复实用涨点，接受成熟方法适配，不要求强算法创新。总设计及阶段准入已写入项目README。当前没有新增GPU生成、训练、API调用或模型/视频下载；只读取约130KB官方研究源码/既有Video-MME公开时间标注，并做CPU诊断。既有候选全部保留，本次不是新方法准确率结果。

## 1. 当前设计与最重要的修正

拟议架构：问题条件化时间选择＋Mage原生Codec稀疏视觉表示＋真实时间对齐字幕。Codec包括canvas和来源patch/时间映射，不是单纯空间ROI；硬裁选段后接Codec并非天然更优。必须先证明语义选择的新增题收益，再验证Codec接入，最后做四组Codec/Codec＋字幕/语义Codec/语义Codec＋字幕，保留Frames-32＋连续字幕实际参考。

当前代码的实际情况：condition_clips.py将first/earliest归为first_event，并固定保留0–12、12–24秒两个窗口。它没有把“first six minutes”解析为0–360秒范围；第一个事件也可能发生在片头以后。因此目前只是规则化检索，不能称为完整时间条件理解。所有后续改进独立版本，不覆盖冻结结果。

## 2. 已做的小规模尝试：既有30题的KFS离线诊断

采用[官方KFS-Bench](https://github.com/NEC-VID/KFS-Bench)的Video-MME证据区间，仅作离线评估，不进入选择器。不引入新视频、自制评测集或新答案。原parquet通过已有miniconda的pyarrow读取；Mage环境没有安装新依赖。

按videoID＋完整问题＋四选项精确匹配原question_id：本地625是795-2，不能按index/3推算。30题均完成身份核验，只有13题有公开标注（旧12中7、新18中6）；其余17题明确排除，不记零分。采用官方eval.py的end+1秒边界及UKSS计算，已用官方脚本交叉核对。

已有方法在13题上的平均必需场景命中率SHR：均匀42.31%，带观察v2为80.77%，去观察73.08%。完整覆盖所有标注场景的题数分别5、10、9。平均KFR分别3.61%、13.62%、14.33%；官方UKSS分别0.0536、0.2460、0.1898。它们是时间覆盖指标，不是QA准确率或语义充分性认证，也不代表其余17题。

去观察版本379/325/454全部命中标注场景但QA仍错。特别是325的证据区间54–175秒较宽，17帧落入区间仍可能没满足人物身份、采访状态、相对时间等细条件。不能把这个现象直接断言为Mage能力不足；还可能是场景标注粗、瞬时细节/对象关系不对或干扰画面影响。

去观察版本遗漏标注场景的题为401、347、596、549。13题中未发现“局部窗口与必需区间相交但所有4帧均未命中该区间”的案例；1fps候选池也都能覆盖这些标注。因此当前没有直接依据把局部加密列为第一优先。这不证明瞬时动作永远不会漏：公开区间较粗，且17题无标注。

新增18题中只有6题被KFS标注覆盖：均匀与去观察均完整覆盖2题，带观察v2为3题。小样本覆盖也没有证明去观察方案在新增题有优势。所有数据与逐题缺失标记保存于research_conditions_20261105/kfs30_*.json。

## 3. 已做的小规模尝试：官方AKS默认参数CPU影子选帧

阅读并执行[官方frame_select.py](https://github.com/ncTimTang/AKS/blob/main/frame_select.py)的选择函数。复用旧1fps图像特征与完整原题/ABCD文本向量，K32、ratio1、t1=.8、t2=-100、depth5，参数未按标注调整。只生成30题影子帧号，不生成新QA或特征；然后对相同13题做官方覆盖评估。

结果：SHR65.38%，KFR6.01%，UKSS0.1260。30题均展开到深度5的32个时间桶，每桶取1个高分帧。说明在本地CLIP分数及这组默认参数下，它实际更接近分层时间覆盖，而非强条件推理。不能据此否定AKS论文，也不能将覆盖数值当QA效果；它与当前6窗口/8锚点结构不完全同构，不是只改一个内部参数的严格消融。当前不值得仅为论文名气立即跑其GPU实验或大量扫阈值。

工程注意：官方CLI将t1声明为int而默认值为0.8；恒定分数min-max需处理；预算取整/短视频需保护。本次直接调用函数传入0.8，30题分数均有效且恰好32帧，没有靠修补/调参制造好结果。影子选择先全部落盘，之后才读取标注评估。

## 4. 最贴合完整条件问题的成熟思路：HiMu

[官方项目](https://github.com/DanBenAmi/HiMu)、[论文](https://arxiv.org/abs/2603.18558)。本次读取logic.py、llm.py、selection.py、config.py实际代码，不只依据摘要。

值得借鉴的是：把整题拆成可见的叶谓词，先各自定位，再按已知条件组合分数曲线，避免整题＋四个答案被压成一个模糊相关性方向。logic.py有AND、OR、SEQ、RIGHT_AFTER；llm.py明确：如果题目让模型推断未知顺序，不得将某个候选答案顺序写成SEQ，应独立检索子事件，交给下游根据真实时间判断。这可防止625类顺序题发生选择阶段答案泄漏。

但是逻辑组合不是充分性证明：低质量CLIP叶定位不会因加AND/SEQ自动变真；OR也不保证每个子事件都被最终预算覆盖。必须检查子事件预算/覆盖，不能将单条综合曲线的高峰当成找齐所有事件。first/last/count/not没有原生完整算子，不能宣称HiMu现成解决所有瓶颈。

完整官方配置依赖文本LLM以及额外视觉/文字/音频专家；仅复用现有CLIP的轻量版本是适配实验，不是官方复现。语音/对话依赖题不能指望纯CLIP找出说话含义；视觉同一人物跨段关系也可能需要更强定位。必要信息不在画面中时，应将字幕信息贡献单独报告，不能包装成纯视觉改进。

## 5. 不优先整套迁移的路线

[VideoTree](https://github.com/Ziyang412/VideoTree)和[LVNet](https://github.com/jongwoopark7978/LVNet)有可参考的层次表示/粗到细思想，但完整实现引入额外特征、caption或LLM调用，不是现有CLIP pooled缓存的直接替换。现有Mage事实报告不可靠，不应再次把它当独立裁判。

[MDP3](https://github.com/sunh-23/MDP3)研究相关性、集合多样性和顺序；可作为后续覆盖/冗余对照，不替代完整题意和细动作落地。当前不并行堆入多种选择器，不用多次规则搜索挑最好结果。

[KFS-Bench](https://github.com/NEC-VID/KFS-Bench)是评估标注与代码，不是选帧算法；其研究用途许可证随源码快照保存，不将其代码作为生产系统组件发布。

## 6. 推荐下一步：先把“条件”落地，而不是重启自我判决器

下一次只验证“问题条件化检索”，不同时接Codec、字幕、加帧或答案覆盖：

1. 原问题/完整选项为唯一解析输入，解析器只输出可见对象/事件、已知关系及明确时间范围；不看视频、人工位置、GT或旧答案。未知顺序不预设；why/否定/口述事实不能强行改成视觉可证条件。
2. 先在30题上做盲于答案的解析接口审阅：first six minutes必须是0–360秒；first magic是待查事件顺序而非0–24秒；order必须保留所有显式子事件；空间排列不等于跨视频顺序。结构非法或能力不支持时明确回退原查询，不能按答案补规则。
3. 仅编码新增子谓词文本，继续复用旧图像特征。固定当前32帧、6窗口、全局锚点与QA配置，先比较查询表示/条件是否确实改善检索，而非一起改变所有模块。时间算子必须用真实秒数，不能把不规则采样位置当严格等间隔帧。
4. 先查看叶谓词落地与官方覆盖诊断；不能用人工标注设置逐题窗口，不能按GT选择参数。若仍只找到同物体却错事件，说明CLIP本身的动作/实体绑定不足，需停止对相似度套复杂逻辑，而不是继续宣称条件已解决。
5. 冻结一个候选后才进行受限QA，再在剩余开发题上单独报告新增收益。已见30题仍只作开发与机制诊断，不称独立测试；旧12改善不替代新增部分结果。

解析器的实现选择待定：官方使用文本LLM，当前不能假定Mage在新文本任务上可靠，也不能未经用户确认调用DeepSeek或下载新模型。本次未运行文本LLM或API。因此当前已完成的是研究与CPU诊断，不是HiMu-lite工程或涨点结果。

若用户更重视最终整体问答收益，可另讨论字幕/音频作为时间检索线索的多源路线；这会改变输入信息范围，必须与同样能访问这些信息的原Mage公平对比，不算纯视觉选帧贡献。现有冻结Frames-32＋连续字幕保持当前实际参考，不被新假设取代。
